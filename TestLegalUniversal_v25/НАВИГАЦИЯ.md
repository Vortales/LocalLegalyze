# НАВИГАЦИЯ.md — карта проекта Legalyze Universal v25

> **Назначение файла.** Это не документация «для пользователя» и не отчёт о версии
> (это `README.md`). Это **карта кода**: что за что отвечает, где именно лежит,
> как данные ходят между модулями и куда смотреть, когда что-то сломалось.
> Читается за 10 минут вместо чтения 23 000 строк.

> Все номера строк указаны для коммита `cc5162a` (v25). Если строки «съехали» —
> ищите по имени символа: имена в этом файле точные.

## 0. Что это за программа (одним абзацем)

`Legalyze` — настольный клиент Windows: в окне собственного GUI открывается
**встроенное окно настоящего Chrome** со страницей ИИ-чата Google (`google.com/ai`
или `gemini.google.com`). Клиент **сам держит в этом чате два вложенных файла**:

1. `*.pdf` — выбранный «промт» (расшифровывается из файла, полученного с сервера);
2. `Шаблон.txt` — карточка данных пользователя (`Name/ID/Fraction/Rang/Department/JobTitle`).

Дополнительно: глобальные горячие клавиши (микрофон/показ окна), штатная запись
голоса страницы, зум 67 % для точной раскладки, счётчик запросов с сервера,
авторизация по логину/паролю с привязкой к HWID, авто-обновление версии.

**Три опоры архитектуры:**

| Опора | Модуль | Суть |
|---|---|---|
| Окно чата | `native_browser.py` + `win32_embed.py` | Chrome запускается отдельным процессом и его HWND **вживляется дочерним** в Qt-плейсхолдер (QtWebEngine не умеет штатный микрофон Google) |
| Управление страницей | CDP (DevTools) в `main.py` | `CDP.eval()` / `CDP.send()` — единственный способ читать и нажимать что-либо на странице |
| Содержимое чата | `PromptLoaderWorker` + `UploadThread` | промт скачивается/расшифровывается в PDF, затем оба файла «впрыскиваются» в чат через `DataTransfer` |

## 6. Разбор дефекта: «после нескольких запросов в чате появляются лишние PDF и Шаблон.txt»

Симптом из обращения: `Окно чата → Memphis.pdf Шаблон.txt Memphis.pdf Шаблон.txt`,
и со временем GUI начинает подлагивать.

### 6.1. Причина №1 (главная): два независимых «критерия готовности», и повторный впрыск без ожидания

`UploadThread.run()` (`main.py:3646–3690`):

```python
present = int(state.get("present", 0) or 0)
names   = state.get("names", []) or []
names_ok = any(str(n or "").strip() for n in names)

if names_ok:
    missing  = self._missing_files(names)
    complete = present >= REQUIRED_CHAT_FILES and not missing   # критерий А
else:
    missing  = []
    complete = present >= REQUIRED_CHAT_FILES                   # критерий Б
```

Далее впрыск (`3708–3745`):

```python
to_upload = list(missing) or (
    [pdf, template] if present < REQUIRED_CHAT_FILES else []
)
...
for path in to_upload:
    injected = upload_file_advanced(self.page, path)
    time.sleep(0.3)          # ← пауза ПОСЛЕ впрыска, а не до новой проверки
```

Что происходит на реальной странице:

1. Впрыск **не появляется в DOM мгновенно**: Google создаёт чип позже (загрузка
   файла, 0.5–3 с). Всё это время `JS_CHECK_FILES` возвращает `present = 0`.
2. Через 0.3 с круг повторяется: `present = 0` → снова `to_upload = [pdf, template]`
   → **второй впрыск того же**. Причём `upload_file_advanced` отправляет файл
   **двумя механизмами сразу** — `input.files = dt.files` + `change` **и**
   `dragenter/dragover/drop` на композер. Каждый из них может создать свой чип.
3. Когда чипы наконец появляются, их уже 4: `Memphis.pdf`, `Шаблон.txt`, и по
   второму разу. `present = 4`.
4. Дедупликация (`3671–3685`) написана, но срабатывает **только** при
   `present > REQUIRED_CHAT_FILES + 2`, то есть при `present > 4` — а 4 не больше 4.
   И `_dedup_done` ставится один раз за жизнь потока, поэтому следующая волна дублей
   уже не лечится вовсе.

Итог: чем медленнее страница отвечает (несколько запросов → больше чипов в DOM →
медленнее `JS_CHECK_FILES`), тем чаще срабатывает «ещё не появилось — впрыснем ещё».
Порог `> 4` и одноразовый `_dedup_done` делают дефект **неизбежным на медленной машине**.

### 6.2. Причина №2: лаги GUI — это не «нагрузка браузера», а синхронный сбор логов

На каждом круге `UploadThread` (30–50 раз в секунду) выполняется:

* `check_state()` → `page.eval(JS_CHECK_FILES, timeout=2)` — round-trip в DevTools;
* **`log_page_probe(page)`** каждые 5 с — ещё один `eval` (плюс `probe_page_surface`);
* **`btrace.audit_export(...)`** на **каждый** впрыск — читает файлы и считает
  `SHA-256` каждого (PDF на несколько МБ), затем ещё `eval(JS_EXPORT_AUDIT)`;
* **`btrace.capture_page(full=True)`** при `upload_blocked` — выгружает **весь HTML
  страницы** (единицы МБ) и пишет на диск;
* `btrace.mark` на каждый хоткей + `monitor_window` + `_trace_qt_tick` раз в 100 мс.

Всё это идёт из фонового потока, но конкурирует за **тот же websocket** (`CDP._lock`)
и за **тот же GIL**, что и отрисовка GUI. Чем больше файлов в чате — тем длиннее
`innerText`/`querySelectorAll` в `JS_CHECK_FILES` и тем заметнее просадка.

### 6.3. Причина №3: «двойной» критерий `_has_both_files` и подстрочное сравнение имён

`_chat_has_file()` (`main.py:1657`) сравнивает подстрокой **в обе стороны**:

```python
if want in text or text in want:      # "pdf" ⊂ "Memphis.pdf"
    return True
```

Поэтому чип с именем `Memphis.pdf` «удовлетворяет» любой `wanted`, который является
его подстрокой (например, второй промт `Memphis`), а `present >= 2` считается
«готово» даже когда в чате `Memphis.pdf Memphis.pdf` — оба чипа одноимённые,
а `Шаблон.txt` нет. Отсюда «прикреплено», хотя фактически нет.

### 6.4. Что сделано в локальной версии

`LocalLegalyze_Local.py` заменяет `UploadThread` на **`PageController`**
(раздел 15 файла; правило вложения — `plan_attachments()` в разделе 14):

1. **Один механизм впрыска** — только `input[type=file]` + `change`; `drop`
   применяется **лишь если** поля файла на странице нет. Один вызов = максимум один чип.
2. **Пауза ДО повторной проверки** (`HOLD_AFTER_INJECT = 1.6 с`): пока чип не появился,
   монитор просто ждёт и ничего не впрыскивает.
3. **Никаких «двух критериев»**: каждый круг считается точное сопоставление
   «желаемое → найденное по имени», с привязкой каждого чипа к своему файлу.
4. **Безымянный чип считается «возможно уже этот файл»** — он подавляет повторный
   впрыск (в оригинале отсутствие имени вело к `names_ok = False` → впрыск всего набора).
5. **Обрезка лишнего** (`prune`): если чипов больше, чем нужно, лишние удаляются
   **по одному за цикл** с проверкой после каждого. Дубликат `Memphis.pdf` больше
   не остаётся в чате.
6. **Сравнение по нормализованному имени** (полное совпадение → подстрока → стем),
   а не «подстрока в любую сторону».
7. **Никакого тяжёлого сбора логов**: один `eval` на круг, простой текстовый лог на
   50 строк в памяти, без `SHA-256` файлов и без выгрузки HTML.
8. **Смена файла = замена, а не «уже вложено»**: у шаблона постоянное имя
   `Шаблон.txt`, поэтому перед повторной подготовкой старые чипы снимаются
   (`removed` в логе), и только затем вкладываются новые. Иначе новый текст
   шаблона не доезжал до модели — в чате оставался прежний файл.
